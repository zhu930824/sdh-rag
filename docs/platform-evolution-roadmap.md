## 1. 结论

平台下一阶段不应继续以“增加更多聊天能力”为主，也不应因为功能变多就立即改造成微服务。当前最有价值的升级，是把已经具备的知识接入、RAG、评测、知识发布和 Agent 执行能力，收敛成一套能够稳定解决业务问题的闭环：

```mermaid
flowchart LR
    S[业务场景与目标] --> K[可信、可治理的业务知识]
    K --> A[可控 Agent 执行]
    A --> O[业务结果与运行轨迹]
    O --> E[自动评测 + 人工复核]
    E --> I[知识 / Prompt / 工具改进]
    I --> G[回归门禁与灰度发布]
    G --> A
```

建议同时推进两条主线：

1. **生产底座线**：安全配置、可靠任务、全链路可观测性和成本治理。
2. **产品价值线**：Agent Evaluation、业务场景工作台、业务知识建模和结果闭环。

下一项产品功能应是 **Agent Evaluation MVP**；正式扩大生产使用前，必须先完成 P0 安全治理。

## 2. 趋势判断

### 2.1 从“回答评测”转向“轨迹评测”

Agent 的质量不能只看最终答案，还要检查任务是否完成、工具是否选对、参数是否正确、是否触发了不必要或越权的动作，以及失败发生在哪一步。OpenAI 的 Agent 评测与 Trace Grading 已把端到端决策、工具调用和运行步骤作为可复现评测对象，这与平台现有的 Agent 轨迹和评测实验室天然衔接。

参考：[OpenAI Agent Evals](https://developers.openai.com/api/docs/guides/agent-evals)、[OpenAI Trace Grading](https://developers.openai.com/api/docs/guides/trace-grading)

### 2.2 从“私有埋点”转向“统一 GenAI 可观测语义”

模型调用、Agent 调用、工具执行、检索和 Token 使用正在形成统一的可观测语义。平台应基于 OpenTelemetry 建立 trace，并使用 `trace_id / run_id / task_id` 串联一次业务请求；Prompt、工具参数和结果可能包含敏感数据，必须默认脱敏或关闭正文采集。

参考：[OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)

### 2.3 工具生态会标准化，但权限边界比接入数量更重要

MCP 的 Host—Client—Server 分层适合成为未来连接器和工具适配边界，但不能把 MCP 等同于“开放全部业务接口”。远程工具应具备独立身份、最小权限、Token audience 校验、审批和审计，禁止把上游 Token 原样透传给下游。

参考：[MCP Architecture](https://modelcontextprotocol.io/specification/2025-06-18/architecture)、[MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

### 2.4 评测应成为风险治理流程，而不是一次性测试

生成式 AI 风险需要贯穿治理、场景识别、度量和持续管理。平台已有数据集、人工复核和发布门禁，下一步应把高风险业务场景、红队样本、权限边界和安全拒答纳入版本发布条件。

参考：[NIST AI RMF Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)

## 3. 能力差距与优先级

| 优先级 | 当前基础 | 主要缺口 | 目标结果 |
|---|---|---|---|
| P0 | JWT、知识库权限、审批与审计；第一轮配置与管理接口加固已完成 | 外部凭据轮换、Secret Provider、租户隔离和 CI 安全门禁仍待完成 | 达到可进入生产环境的安全基线 |
| P1 | 应用内线程池、Scheduler、Redis 锁 | 异步任务的租约、心跳、取消、死信和一致性协议不统一 | 任务可恢复、可追踪、不重复产生副作用 |
| P2 | RAG 分层评测、实验室、Agent 运行轨迹 | 缺少工具与步骤级评测、Agent 回归集和发布门禁 | Agent 变更可以量化比较和安全发布 |
| P3 | 知识源、图谱、发布、版本与反馈回流 | 知识仍以文档为中心，业务对象、时效、规则冲突和结果归因较弱 | 知识真正嵌入业务流程并影响业务指标 |
| P4 | 工具注册、REST 连接器、Webhook | 缺少标准扩展协议、租户配额、模型路由与插件生命周期 | 形成可扩展的平台生态与规模化运营能力 |

## 4. 分阶段路线

### P0：生产安全与配置治理（0—4 周）

目标：消除扩大试用前的高风险项。

- 将数据库、Redis、MinIO、模型 API Key、JWT Secret 等从仓库配置移出，按 dev/test/prod 分层，并轮换已经暴露的凭据。
- 建立 Secret Provider 接口；首期支持环境变量，后续可接企业密钥管理服务。
- 对 Webhook、模型配置、连接器凭据、评测定时任务明确租户和管理员边界。
- 日志默认脱敏 Prompt、Authorization、Cookie、工具参数、工具返回和个人信息。
- 建立数据分类：公开、内部、敏感、受限；检索、导出、模型调用和工具执行均继承资源权限。
- 在 CI 中加入 Flyway 迁移验证、凭据扫描和关键鉴权回归测试。

验收标准：

- 仓库和制品不包含生产密钥或可用默认密码。
- 非授权用户无法读取、触发或重放其他租户的知识、Webhook、评测任务和 Agent 动作。
- 关键操作都能按用户、租户、资源、时间和结果审计。

- [x] 模型、系统设置、计划任务、Webhook、用户、角色和操作日志接口增加后端管理员校验。
- [x] Webhook 增加公网 HTTPS 默认策略、SSRF 防护、连接/读取超时和敏感响应字段隐藏。
- [x] 默认关闭聊天 Prompt/响应正文日志，并清理模型、评测、路由、记忆和工作流中的敏感内容日志。
- [x] 增加管理员授权、生产密钥校验和 Webhook 网络策略单元测试。

### P1：可靠执行与可观测性（第 1—2 个月）

目标：为知识同步、索引、评测、Webhook 和 Agent 动作建立同一套执行语义。

- 抽象统一 `Job` 模型：状态机、优先级、租约、心跳、超时、重试、取消、死信和人工重放。
- 使用数据库原子抢占任务；所有具有外部副作用的动作必须有幂等键。
- 使用 Transactional Outbox 保证“业务事务提交”与“异步事件投递”最终一致。
- 统一 `trace_id / run_id / task_id / user_id / tenant_id`，贯穿 HTTP、检索、模型、工具、数据库和 Webhook。
- 建立运营指标：成功率、P50/P95 延迟、队列积压、重试率、Token、模型成本、空召回率和审批等待时长。
- 为模型和场景配置日/月成本预算、速率限制和降级策略。

#### 执行进度（2026-09-09）

- [x] 新增统一 `platform_job` 数据模型和状态机，覆盖优先级、尝试次数、租约、心跳、退避、取消、死信和重放。
- [x] 使用数据库 CAS 原子抢占和业务唯一 `job_key`，支持多实例竞争与租约过期接管。
- [x] 评测任务与 Job 在同一事务创建，数据集快照保存到持久化 payload，应用重启后可恢复。
- [x] 评测执行增加样本级心跳、协作取消、幂等重跑，并在评测页提供取消/重新执行入口。
- [x] 知识源定时拉取迁移到统一 Job；保留来源级 Redis 锁和 `external_id + content_hash` 幂等。
- [x] 增加当前用户任务中心，展示 Trace、尝试次数、结果/错误，并支持取消与死信重放。
- [x] Webhook 事件接入 Transactional Outbox，并拆分为接收端级可靠 Job；支持稳定投递 ID、退避重试、死信和接收端幂等。
- [x] 打通 HTTP → Outbox → Job Worker → Webhook 的 Trace ID，增加任务积压、24h 成功率、重试、死信与投递告警快照。
- [x] 文档解析、分块与向量索引迁移到统一 Job；增加关系版本、任务绑定、恢复扫描、Redis 互斥、稳定向量 ID 与失败重试。
- [ ] 将评测实验编排和 Agent 动作迁移到统一 Job。
- [ ] 完善 Outbox 管理视图、OpenTelemetry Span、外部告警通道、模型成本指标和预算告警。
- [ ] 增加租户级任务隔离、管理员全局任务视图、预算与限流降级。

验收标准：

- 应用重启后任务可以安全续跑，重复消费不会重复执行外部动作。
- 任一用户投诉可以追溯到知识版本、检索结果、模型配置、工具调用和最终业务结果。
- 超预算、队列积压和连续失败能够告警并触发受控降级。

### P2：Agent Evaluation MVP（第 2—4 个月）

目标：把现有 RAG 评测实验室扩展为 RAG + Agent 统一质量平台。

#### 当前执行进度（2026-11-04）

- [x] P0-1：真实 MySQL 故障验收，覆盖租约、状态发布与事务回滚。
- [x] P0-2：统一运行准备、生命周期和轨迹发布边界。
- [x] P0-3 首批：30 条离线 AgentScope SDK 场景、稳定场景 ID、JUnit 断言和结构化回归报告，详见 [Agent 场景回归集](agent-scenario-regression.md)。
- [x] 场景导入、不可变版本与已结束运行结果归档，含用户隔离、哈希、幂等和评测页入口，详见 [场景版本与运行结果归档](agent-evaluation-archives.md)。
- [x] V36 执行批次配置指纹、模型精确绑定与漂移记录；归档区分完整/部分/空历史，详见 [执行批次配置快照](agent-execution-attempt-snapshots.md)。
- [ ] 知识发布版本绑定、完整可评分证据和可靠场景执行；配置指纹不代替精确重放材料。
- [x] V37 保留召回片段的索引代际和内容指纹、多片段引用及不可改写的检索观察快照，详见 [RAG 检索证据](rag-retrieval-evidence.md)。
- [ ] 索引代际发布可见性与请求读版本保护；观察快照不代替原子发布版本。
- [ ] 真实模型轨迹评分、基线比较和发布门禁。离线协议回归不等于完成 Agent 质量评测。

#### 功能范围（目标）

- **Agent 场景数据集**：输入任务、初始上下文、允许工具、禁止动作、期望结果、关键步骤和风险等级。
- **轨迹回放**：展示每一步模型决策、检索、工具参数、工具结果、审批、耗时和 Token。
- **分层指标**：任务完成率、工具选择准确率、参数正确率、关键步骤覆盖率、无效调用率、平均步骤数、成本和延迟。
- **安全指标**：越权尝试率、危险动作审批召回率、不必要审批率、安全拒答准确率和敏感数据泄露率。
- **失败归因**：知识缺失、检索失败、规划失败、工具失败、参数失败、权限失败、审批失败和业务系统失败。
- **闭环回流**：失败轨迹一键生成回归样本，人工修正期望步骤后进入版本化数据集。
- **发布门禁**：Agent、Prompt、模型和工具版本都保存快照；与基线比较后决定通过、灰度或阻断。

#### 推荐数据模型

- `agent_evaluation_dataset`
- `agent_evaluation_case`
- `agent_evaluation_run`
- `agent_evaluation_step_result`
- `agent_evaluation_grader_result`
- `agent_release_gate`

现有 RAG 数据集、实验、人工复核和 Webhook 告警尽量复用，不再建设第二套评测平台。

验收标准：

- 可用不少于 30 条覆盖正常、边界、权限和失败恢复的 Agent 测试场景完成固定版本回归。
- 任一失败结果可定位到具体步骤，并能转成回归用例。
- Agent 或工具版本变更必须通过任务质量、安全和成本三类门禁。

### P3：业务知识与场景闭环（第 3—6 个月）

目标：从“文档知识库”升级为“业务知识层”。

#### 知识升级

- 建立业务对象模型：客户、产品、订单、工单、合同、政策、流程和指标，而不只保存文档与分块。
- 为知识增加业务元数据：适用组织、角色、地区、产品线、生效时间、失效时间、权威级别和责任人。
- 建立来源血缘、版本差异、重复检测和冲突规则；同一问题出现多个答案时按权威级别与有效期决策。
- 建立知识健康度：新鲜度、覆盖率、使用率、引用率、无答案率、反馈率、冲突率和责任人 SLA。
- 为结构化数据提供只读查询工具，实时状态从业务系统获取，稳定规则和解释性内容从知识库获取。
- 让知识图谱服务于实体消歧、关系扩展和影响分析，避免为“有图谱”而抽取全部关系。

#### 产品升级

- 建设“业务场景工作台”：目标、输入、知识、工具、审批策略、评测集、版本和看板在同一处配置。
- 优先沉淀 2—3 个高频模板，例如客服答复与工单创建、销售方案与 CRM 更新、制度问答与流程办理。
- 输出不止是答案，还包括证据、建议动作、待确认项和可执行按钮。
- 把业务结果回写质量系统，例如工单是否解决、订单是否成功、人工是否改写、处理时长是否下降。

验收标准：

- 至少 2 个业务场景完成“知识回答—受控动作—结果回写—失败回归”的闭环。
- 每个上线场景均有业务负责人、知识责任人、质量阈值和业务 KPI。
- 平台指标能够与一次解决率、人工处理时长、转人工率或流程成功率中的至少一项关联。

### P4：平台化与规模演进（第 6—12 个月）

目标：在真实负载和组织需求出现后扩展，而不是提前复杂化。

- 提供 Connector/Tool SDK，统一凭据、分页、限流、增量游标、幂等、Mock 测试和健康检查。
- 增加 MCP Adapter，把合适的资源和工具通过标准协议接入；每个 Server 保持独立权限与审计边界。
- 建设模型网关：统一模型目录、路由、超时、重试、Fallback、配额、成本和内容策略。
- 支持租户配额、Feature Flag、灰度发布、版本回滚和场景级 SLA。
- 仅在负载或故障隔离证据明确时抽离文档加工、评测、Agent 执行和连接器 Worker。

服务拆分触发条件至少满足一项：

- 单一工作负载长期占用主要 CPU、内存或线程资源。
- 故障需要独立隔离，且当前进程内隔离无法满足 SLA。
- 发布频率、伸缩策略或安全边界与主应用明显不同。
- 已建立领域事件、幂等、统一身份、可观测性和独立运维责任。

## 5. 未来 90 天执行建议

| 时间 | 生产底座线 | 产品价值线 | 关键交付物 |
|---|---|---|---|
| 第 1—2 周 | 凭据迁移、配置分层、日志脱敏 | 定义首批 Agent 场景与指标 | 安全整改清单、Agent Eval 数据规范 |
| 第 3—4 周 | 权限回归、迁移测试、审计补齐 | 准备 30 条 Agent 测试数据 | P0 验收报告、Agent Eval 种子集 |
| 第 5—8 周 | 统一 Job 状态机、幂等键、Trace | 轨迹回放、步骤结果与失败归因 | 可靠任务 MVP、Agent Eval MVP |
| 第 9—12 周 | Outbox、告警、成本预算 | 基线比较、人工复核、发布门禁 | 第一条 Agent 持续回归流水线 |

建议首批 Agent 数据集按以下比例准备：

- 40% 正常业务任务。
- 20% 信息缺失、歧义和需要澄清的任务。
- 15% 工具超时、失败、重复执行和恢复任务。
- 15% 越权、危险动作和提示注入任务。
- 10% 高成本、长轨迹和应当拒答的任务。

## 6. 产品决策原则

新增功能进入路线图前，应回答四个问题：

1. 它解决哪个明确业务场景，业务负责人是谁？
2. 成功结果能否被度量，而不是只评价“回答看起来不错”？
3. 失败时是否能定位、回放、恢复和转成回归样本？
