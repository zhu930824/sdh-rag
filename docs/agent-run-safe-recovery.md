# Agent 运行安全恢复（V34）

## 交付行为

中断或失败的运行现在可以由发起人在聊天页点击“恢复运行”。服务端先判定是否符合恢复条件，再投递到现有可靠任务中心，成功受理后显示排队状态并自动刷新结果。任务中心支持按 `AGENT_RECOVER` 筛选。

此版本开放的是**尚未登记任何业务动作的运行重新执行原问题**，不恢复任意中间帧。恢复会重新调用模型，可能产生额外费用。

## 恢复条件集中在一处

`AgentRunRecoveryPolicy` 是资格判断的唯一来源：

| 条件 | 处理 |
|---|---|
| `INTERRUPTED` 或 `FAILED`，原引擎为 legacy/agentscope，执行批次大于 0，没有有效执行者和任何动作记录 | 允许申请重新执行 |
| 已有任何业务动作记录，包括成功、失败、拒绝、UNKNOWN、GET 动作 | 阻止重新执行，要求核对事实；当前不支持从该断点恢复 |
| 活跃、审批等待、动作等待或已完成的运行 | 不允许申请 |
| 历史无租约运行或未知引擎 | 不允许申请 |
| 调用者不是运行发起人 | 不允许；动作审批人查看权限不等于恢复权限 |

资格展示可以随服务端状态变化；POST 申请和 Worker 启动都重新校验，不能绕过资格判断。运行原有步骤和 Token 计数不因重新执行而清零，运行期仍执行既有预算上限。legacy 续跑同时修正为累计步数及 Token，避免续跑重置预算。

后续[累计预算与取消状态完善](agent-run-budget-and-cancellation.md) 已将剩余预算检查前移到恢复诊断、申请和 Worker 启动，并保存 SDK 已报告用量。额度耗尽时不再受理新的恢复；已进入执行阶段的主动取消按 CANCELLED 收尾。

## 数据和可靠投递

V34 增加 `agent_run.recovery_generation`、`recovery_job_id` 及查询索引。恢复状态和历史回答通过原有数据库提交，没有新增消息队列。

| 过程 | 原子边界 |
|---|---|
| 用户申请 | 锁定 Run；核对归属、租约、动作账本；代际递增；登记 `agent-recover:<runId>:<generation>` 任务；写 `RECOVERY_QUEUED` 及聊天占位回答 |
| 重复申请 | 已排队则返回同一任务；并发申请由运行行锁串行决定，不创建第二个任务 |
| Worker 启动 | 校验持久化任务、归属、代际、执行者与状态；再次核对动作账本；仅删除该用户/运行的 SDK 状态并清空旧轮次文本；置 RUNNING |
| 实际执行 | 复用原问题、证据、引擎、记忆开关与现有决策循环；领取新的 V33 执行批次，使用当前可用工具与模型配置 |
| 启动准备失败 | 尚未领取 Run 租约时退回 INTERRUPTED；已经领取租约的执行不会被准备失败处理覆盖 |
| 排队任务取消、终止或丢失 | 定时核对后退回 INTERRUPTED，让发起人重新申请；不自动重放模型 |

恢复任务最多自动尝试 1 次。下一次由发起人明确申请时创建新代际；旧任务迟到或通过任务中心重新投递，也不能启动新的恢复代际。

恢复执行将任务归属检查接入 Run 租约：流式事件/工具调用检查点最多每秒检查一次，独立 Run 心跳也会检查任务执行权。取消属于协作式停止，不保证立即中断已发送的模型网络请求。已经提交的业务动作仍保留原有独立执行契约，不因取消模型循环而自动撤回或重新发送。

## 聊天与 API

- `GET /api/agent/runs/{runKey}` 增加 `canRecover` 和 `recoveryReason`，仅发起人得到可恢复资格。
- `POST /api/agent/runs/{runKey}/recover` 使用当前登录人身份，返回 `jobId`、`generation` 和 `status`。
- 聊天按钮先读取最新服务端事实，再提交申请；切换会话后迟到的响应不修改当前会话。
- `RECOVERY_QUEUED` 保持轮询；最终回答覆盖原中断或排队提示。恢复受理不创建重复聊天问题。
- 修复“首次回答发布前中断”的历史关联：中断/恢复提示同时写入 `chat_history.agent_run_key`，刷新后仍可定位原运行。

## 验证与部署

后端全量打包、前端行为测试、生产构建和全局类型基线比较均有日志，路径为 `.workbuddy/run-recovery-*.log`。后端数据库测试使用 H2 MySQL 兼容模式和真实 Spring/MyBatis 事务。

后端 146 项测试中 145 项通过、1 项按环境配置跳过，0 失败、0 错误，打包成功。前端 7 项行为测试通过，生产构建通过；既有大分包提示保留。全局类型检查仍为原有 320 条诊断，忽略行号后与基线无新增或改变。`git diff --check` 通过。

部署顺序：按正常 Flyway 流程迁移至 V34，先排空旧决策循环并切换所有后端实例，再更新前端。需要保留处理新任务类型的 Worker；不要把尚未处理的恢复任务交给旧应用。没有在实际 MySQL、真实模型或生产环境执行验证。

不保证跨系统恰好一次；已存在动作记录的检查点关联、UNKNOWN 核对后的恢复、最终 SDK 回答直接回填、SSE 事件游标回放均不在此版本范围。中断模型调用未落库的消耗也无法据此精确补计。
