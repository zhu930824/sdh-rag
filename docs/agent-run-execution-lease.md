# Agent 运行执行权与中断识别（V33）

## 解决的问题

动作队列已有独立的抢占、执行批次和不确定结果处理，但决策循环原先只有 `RUNNING` 状态。两个订阅者可能同时启动；Worker 进程被强杀后，运行可能永久停在 `RUNNING`；旧执行者恢复响应时也可能覆盖较新的结果。

V33 为每次实际执行分配数据库租约和递增批次。legacy 与 agentscope 使用同一套执行权。没有增加另一套调度系统，也没有改变业务动作任务已经提交后的执行契约。

## 数据与状态

| 字段 | 语义 |
|---|---|
| `execution_epoch` | 每次领取执行权原子递增；历史运行默认为 0 |
| `lease_owner` | 单次执行的随机标识，仅服务端持有 |
| `lease_until` | 数据库时间计算的租约到期时间 |
| `heartbeat_at` | 最近一次成功领取或续约的数据库时间 |

领取条件是运行属于该用户、状态为 `RUNNING` 且没有执行者。租约有效期 120 秒，独立的两个守护线程每 15 秒续约，模型阻塞调用不占用心跳线程。续约必须匹配用户、运行 ID、执行者、批次、运行状态和未过期条件，过期租约不能复活。

`RunExecutionLeaseService.guarded` 在短事务中锁住运行行，检查上述执行权，再提交实际写入。网络请求和模型调用不得放在此事务中。行锁使过期扫描、心跳和写入在同一数据库边界串行决定归属。

## 已接入的写入边界

- legacy 每轮调用前检查执行权；轮次快照、步骤和累计使用量在持有执行权时写入。
- AgentScope 每次执行获得独立的受保护状态存储；检查点写入和删除校验用户及运行命名空间、租约与批次，SDK 原有状态版本 CAS 继续生效。
- 工具动作登记在校验执行权的同一事务中写入动作与可靠任务。登记后才发起同步 GET；业务写操作仍由既有动作 Worker 执行。
- 最终答案、失败、暂停状态和聊天历史在同一事务发布，同时释放租约。完整实体更新禁止修改租约字段，避免旧对象覆盖心跳或执行批次。
- 旧的无租约状态迁移不能覆盖当前持有租约的运行。
- 审批回调仅按等待状态更新 `pending_action_id`，不再把整条旧 Run 对象写回。

已提交的业务动作是独立的执行事实。Run 租约到期不撤销已提交动作，也不把它重新发送；动作仍由自身执行版本和状态控制。动作完成服务可以记录真实结果，过期的模型执行者不能再登记新动作或发布回答。

## 中断识别与用户体验

现有恢复扫描器每 15 秒检查最多 100 个候选运行。仅处理 `execution_epoch > 0` 且租约过期的 `RUNNING`；执行者退出后仍遗留 `RUNNING`、最后心跳超过 120 秒的情况也会被识别。扫描器锁行后重新检查，避免误伤刚完成续约的运行。

匹配的运行变为 `INTERRUPTED`，清除租约，并在同一事务更新聊天回答。如果历史回答更新失败，状态变更也回滚。批量扫描遇到失败会由下一次定时扫描重试。

运行详情接口新增 `executionEpoch`、`heartbeatAt`、`leaseUntil`；不返回执行者随机标识。聊天轮询读取到中断状态后停止等待，显示中断原因，并提示先核对业务动作。此轮没有提供直接重跑已有动作的按钮。

## 部署与边界

1. 执行 Flyway 至 V33，增加四个字段和状态/到期索引；保留 V31/V32。
2. 部署时先排空旧决策循环，再切换全部后端实例。旧版本不识别执行权，混合运行无法提供完整保护。使用正常迁移流程，不手工重复执行 SQL。
3. 部署配套前端后，可通过运行详情和聊天中断提示检查状态。

中断识别依赖数据库恢复可用和定时扫描正常工作；不是严格的 120 秒响应 SLA。现有历史 `execution_epoch=0` 运行及尚未进入实际执行的准备阶段不自动判定为中断，避免把旧版本或准备中的运行误当作受保护执行。

V33 完成执行权与中断识别；后续 [V34 安全恢复](agent-run-safe-recovery.md) 已开放“无业务动作记录”的发起人恢复入口，仍没有实现任意中间帧接管。恢复已有动作必须先核对真实 SDK 检查点、工具调用 ID 与动作账本；存在 UNKNOWN 时仍需查询下游或人工核对。当前实现也不保证跨系统恰好一次。

仍保留新运行默认 `AGENT_RUNTIME=legacy` 的选择。没有对真实模型、实际 MySQL 或生产实例进行验证。
