# Agent 执行批次配置快照

本轮将准备阶段的模型选择固定为独立绑定，并在每个执行租约批次第一次调用模型之前，持久化配置指纹。目标是解释一次运行实际提交给执行引擎的输入，以及续跑/恢复时哪些配置发生变化。

## 修复模型绑定

原路径存在两次选择：legacy 先选 `model_config.id`，再按 `model_id` 名称重新查找模型，并允许回退到默认模型；SDK 在执行循环开始时重新读取配置 ID。这会让同名的不同配置相互替代，或让排队期间的新配置替代已准备的配置。

新增回归测试已在旧实现复现同名配置替代。现在初次、续跑和恢复均通过相同准备入口，直接用选中的配置创建模型，不经模型名缓存、不进行供应商默认模型回退。停用配置或无法创建所选模型时明确失败。

`ModelBinding` 防御性复制模型配置，调用者取得的配置也是副本；不会因数据库配置对象或外部副本变化而改变本批次。`Prepared` 只保存这一份绑定，模型 ID、供应商和 legacy 模型对象均从中取得，SDK 也直接使用该绑定的配置副本。业务工具列表和工具对象同样独立复制。

## 持久化边界

Flyway V36 增加 `agent_execution_attempt`，主键是 `run_id + execution_epoch`。写入通过现有执行租约服务的受保护事务完成：先锁定并验证 Run 的所有者、批次和有效租约，再追加快照。

- 首次执行、审批后续跑和安全恢复都走同一个协调入口。
- 同批次重试且指纹相同，返回已有快照；同批次不能覆盖为另一份配置。
- 旧租约不能写新快照或替换历史记录。
- 唯一键冲突后的当前读能在旧 REPEATABLE READ 快照下返回已经提交的同一批次。
- 快照写入失败时，模型和工具均不会启动，运行通过既有失败发布边界收尾。
- 快照与调用模型之间不持有数据库事务锁；Run 心跳继续使用现有租约机制。

每条快照包括引擎、模型配置、Prompt、工具、知识证据和运行设置六个区段的指纹，并记录前一已知批次及 `changedSections`。配置内容按稳定键序列化计算 SHA-256；时间和批次编号不参与配置指纹，单纯领取新租约不会被当成配置变化。

| 区段 | 保存内容 |
|---|---|
| 引擎 | 当前执行引擎/版本及原 Run 记录的版本 |
| 模型 | 配置 ID、供应商、模型名称、配置温度/Token 参数、更新时间、endpoint 的哈希 |
| Prompt | 实际传入的 system 与续跑注记的哈希 |
| 工具 | 工具 ID、代码、定义指纹、名称/描述哈希、超时与状态 |
| 知识证据 | 知识库 ID、实际传入证据文本的哈希、知识发布绑定状态 |
| 运行设置 | 记忆开关、整体步骤预算 |

API Key、认证头、凭据引用、endpoint 原文、Prompt 原文及证据正文不写入这张表；凭据本身不参与配置哈希。哈希用于配置差异定位，不提供原文恢复能力。SDK 状态、既有聊天消息和工具动作账本继续使用原来的存储和权限。

配置中的温度和 Token 值是配置值，未填写时仍沿用相应引擎版本的默认值，不将它们伪装为服务端已报告的有效参数。当前 RAG 检索没有在 Run 中固定发布版本，因此有知识库时明确记为 `UNPINNED`，无知识库为 `NOT_APPLICABLE`；证据哈希不能冒充知识发布版本。

SDK 版本从当前加载 JAR 的 Maven 元数据读取，缺失时标为 `UNKNOWN`，不会沿用旧 Run 的版本来冒充新批次运行时版本。legacy 的 `1` 是现有平台协议标签，并非应用源码构建号。

## 评测归档

运行结果归档升级为快照 schema v2，在原有轨迹之外复制 `executionAttempts`：

- `COMPLETE`：有执行批次，且从 1 到当前 epoch 的记录连续完整。
- `PARTIAL`：只有部分批次有记录，例如升级前开始、升级后续跑的任务。
- `NONE`：历史任务没有执行配置快照。

只有完整历史才在顶层给出模型、Prompt、工具版本指纹；跨批次版本不同显示 `MULTIPLE`，完整历史缺失时仍为 `UNKNOWN`。每批次指纹和变化列表可单独查看。旧归档保持不可变，不被后台“补齐”为最新配置。

本轮没有增加自动场景执行、自动评分、版本锁定或精确重放承诺。知识发布未固定、Prompt/工具实现代码未完整保存、供应商默认参数可能变化，均不能仅靠配置哈希还原一次运行。

## 验证与行动记录

1. 核对当前工作区、路线图和三类执行入口，定位两次模型选择的问题。
2. 在旧实现复现同名模型配置替代，再改为直接配置绑定，移除协调服务对模型配置服务的重复依赖。
3. 增加空实现下失败的批次快照测试，再实现租约保护、追加写入、同批次幂等及变化区段。
4. 固定模型与工具的对象所有权，验证外部修改不能改变已准备输入。
5. 验证快照写入先于两种引擎的模型调用，失败时不会消耗模型 Token。
6. 使用真实 SDK 验证恢复会话采用本批次系统提示词及模型配置。
7. 验证评测归档区分完整、部分和空历史，并保留跨批次变化。
8. 将真实 MySQL 验收扩展到 V36，验证旧 Fence、事务回滚及旧快照下重复写入。

- 原实现的同名模型替代回归准确失败，显示选中了另一个配置创建的模型；修复后通过。
- 批次快照空实现下的行为测试失败，补充实现后，配置绑定、快照、协调入口和归档定向测试 32 项全部通过。
- 真实 SDK 的恢复提示词/模型配置用例通过，SDK 运行时测试合计 7 项通过。
- 最终完整 `verify`：普通测试 222 项，其中 221 项通过、1 项沿用已有环境配置跳过；真实 MySQL 14 项全部通过、无跳过；后端打包成功。
- MySQL 验证 V1—V36 迁移与重复执行、旧 Fence 隔离、回滚无残留、旧快照重复捕获，以及归档保留完整批次历史。测试数据库及 Worker 已退出。
- `git diff --check` 通过。本轮未修改前端生产代码，不重复前端构建和全局类型检查；上一轮记录的 320 项既有类型诊断仍属后续待治理项。
