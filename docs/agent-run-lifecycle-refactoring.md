# Agent 运行生命周期收敛（P0-2）

本轮将两种引擎和续跑路径共用的准备、进度及发布逻辑提取为明确的应用边界，沿用原有数据库事务、执行租约、审批和可靠任务，不增加迁移或外部服务。

## 职责分工

| 组件 | 职责 |
|---|---|
| `AgentAskService` | 协调问答、检索、执行租约、引擎调用、工具回调及既有 SSE 协议 |
| `AgentExecutionPreparation` | 初始执行与续跑共用的模型配置、供应商白名单、模型创建回退和系统提示词/记忆上下文准备 |
| `AgentRunLifecycle` | 完成、暂停、失败/取消、拒绝与进度的统一发布；不执行模型或发送 SSE |
| `AgentRunTrace` | 从步骤构造有大小上限的完整 JSON 轨迹；纯函数，不读数据库或调用模型 |
| `RunStateService` | 原有 Run/步骤持久化、执行权校验、状态 CAS，以及 Run/回答/租约原子提交 |
| 恢复服务与任务处理器 | 保留恢复资格、任务代际、排队和激活的独立事务边界 |

初始执行和续跑仍保持原有错误文本、模型选择顺序、供应商白名单、工具可见范围、记忆开关和证据快照。`Prepared` 及对外 API/SSE 字段兼容；没有通过更换默认引擎改变执行行为。

## 发布边界

`AgentRunLifecycle.Context` 只携带执行 Fence 与来源/路由元数据，避免把整个聊天服务或 SDK 对象传入状态发布。不可变 `Progress` 统一表示步骤、输入/输出和总 Token，拒绝负数或总量低于输入/输出之和的非法值。

- 完成与暂停使用同一个持久化发布入口，以 RUNNING 和有效执行租约作为前置条件。
- 失败/取消重新读取已保存用量，沿用 `AgentRunTermination` 分类，不清零进度。
- 拒绝仅对等待中的 Run 发布；重复拒绝不会覆盖终态或重新调用模型。
- SDK 用量和 legacy 轮次均通过同一个进度方法保存。legacy 轮次文本与计数仍在同一受保护事务中写入。
- 只有持久化发布成功才发送对应暂停/终态事件。SDK 文本增量仍可先于最终提交到达，这不等于增加了事件回放能力。

恢复排队、激活和续跑的启动 CAS 保留在原协调入口。它们属于命令受理/执行权边界，不与结果发布重新拼成一个长事务。

## 两项行为修复

### 大轨迹保持 JSON 完整

原实现序列化步骤后直接取前 50 Ki 字符，可能截断字符串或对象，导致历史回放无法解析。回归测试在原实现中已复现。

现在最多保留前 50 个步骤，在每次追加完整步骤后检查总长度；超过 50 Ki 字符则保留此前完整的步骤列表。单步预览上限沿用原值：参数 2 Ki、结果 6 Ki 字符。不会保存半个 JSON 对象。

### 记忆失败不改变已提交回答的完成结果

原实现先提交最终回答，再写记忆；记忆异常会进入模型循环失败处理，出现“数据库已完成，但流返回 error、没有 done”的情况。回归测试已复现。

现在回答成功发布后，记忆写入异常只记录关联 Run 的告警，继续返回 `done`。记忆写入仍为同步尝试，没有增加可靠重试任务，也不承诺异常情况下记忆一定补齐。

## 验证方法

重构前增加公共入口行为测试，固定 legacy/AgentScope 完成、审批/后台动作挂起、失败与取消、执行权冲突和旧 Fence 行为；同时复现大轨迹和记忆异常问题。准备服务单独验证两类入口使用同一模型规则，以及记忆开关和原用户/会话参数。

真实 MySQL 验收现通过 `AgentRunLifecycle` 验证旧执行者不能覆盖新结果，并新增历史回答写入失败时，完成状态、计数和租约释放全部回滚的用例。

完整 `verify` 已通过：普通测试 173 项中 172 项通过、1 项按原配置跳过；真实 MySQL 9 项全部通过、无跳过；打包成功。前端 8 项行为测试及 `git diff --check` 通过，测试进程已退出。
